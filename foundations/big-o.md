**Big-O（大 O 记号）**用来描述当输入规模 $n$ 变大时，[算法](../algorithms/)所需的时间或内存大致**怎么增长**。它是衡量算法「能不能扩展」的标准尺子。

## 直观理解

Big-O 不关心「跑了几毫秒」，而关心「**数据翻倍，开销翻几倍**」。它故意忽略常数和低阶项，只看增长的「形状」。

打个比方，给一群人发通知：

- 在群里发一条公告 —— 不管多少人都是一步。这是 $O(1)$，**常数时间**。
- 挨个打电话 —— 人翻倍，电话翻倍。这是 $O(n)$，**线性**。
- 让每个人都去和其他每个人握手 —— 人翻倍，握手次数翻四倍。这是 $O(n^2)$，**平方**。

$$O(1) < O(\log n) < O(n) < O(n\log n) < O(n^2) < O(2^n)$$

排在越左边越好。注意 $O(2^n)$ 这种**指数级**：$n=50$ 时就已经是天文数字，基本「跑不动」。

## 核心要点

怎么读出一段代码的复杂度？看循环的嵌套结构：

- 没有循环、只是几句赋值 → $O(1)$。
- 一层循环扫一遍数据 → $O(n)$。
- 两层嵌套循环都跑 $n$ 遍 → $O(n^2)$。
- 每次把问题规模砍一半 → 出现 $\log n$。
- 分治 + 每层都扫一遍（如归并排序）→ $O(n\log n)$。

两条简化规则：

- **去掉常数系数**：$O(3n)$ 写成 $O(n)$。
- **只保留最高阶项**：$O(n^2 + n)$ 写成 $O(n^2)$。

Big-O 默认描述**最坏情况**的增长上界。

## 一个例子

下面三个函数复杂度各不相同：

```python
def first(arr):              # O(1)：只看第一个元素
    return arr[0]

def total(arr):             # O(n)：扫一遍
    s = 0
    for x in arr:
        s += x
    return s

def all_pairs(arr):         # O(n^2)：每对都比一次
    dups = []
    for i in range(len(arr)):
        for j in range(i + 1, len(arr)):
            if arr[i] == arr[j]:
                dups.append((i, j))
    return dups
```

数据从 1000 涨到 100 万（1000 倍）时大致的影响：

| 复杂度 | 数据 ×1000，耗时大约 ×… |
|---|---|
| $O(1)$ | ×1（几乎不变） |
| $O(n)$ | ×1000 |
| $O(n\log n)$ | ×1000 多一点 |
| $O(n^2)$ | **×100 万** |

`all_pairs` 在 1000 个元素上瞬间完成，在 100 万个元素上可能要跑几个小时——**这就是为什么复杂度比机器快慢更要紧**。

## 在时间序列预测中的意义

长序列预测里，复杂度直接决定可行性：

- 朴素的[自注意力](../attention/)（[Transformer](../transformer/)）对长度 $n$ 的序列是 $O(n^2)$，序列一长，显存和时间都爆炸——这正是各种「高效注意力」想解决的问题。
- **FFT** 把频谱分析从 $O(n^2)$ 降到 $O(n\log n)$，长序列的周期分析才变得可行。
- **KUN / Kernel U-Net** 通过逐层下采样把序列变短，避免在原始长度上做昂贵运算，本质上是在用结构换取更低的复杂度。

数据量从几千个时间点涨到上百万时，**$O(n^2)$ 和 $O(n\log n)$ 的差别，就是「跑不动」和「几秒出结果」的差别。**

## 常见误区

- **把 Big-O 当成精确秒数**：它只描述增长趋势，不是计时器。小数据上 $O(n^2)$ 可能比 $O(n\log n)$ 还快（常数小）。
- **忽略空间复杂度**：内存也会用 Big-O 衡量，缓存换速度时尤其要算清楚。
- **以为最高阶项总是主导**：只有 $n$ 足够大时才成立；小 $n$ 时常数项可能更要紧。
- **把「最坏」当「平均」**：二分查找最坏 $O(\log n)$，但要先满足「数据已排序」的前提。
