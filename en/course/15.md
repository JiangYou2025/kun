## 15.1 Why multivariate deserves its own lecture

In reality you rarely have just one series: temperature, humidity and pressure change together; hundreds of stocks move in concert; the loads of hundreds of regions on one power grid are interlinked. **The interactions between variables are information in their own right** — using humidity to help forecast temperature, or neighbouring road segments to help forecast this one, is often more accurate than looking at a series alone. This lecture explains how to exploit these cross-variable relationships, and a counter-intuitive fact: **sometimes ignoring them is actually better**.

## 15.2 Formalization

At each time step a multivariate series is a vector $x_t \in \mathbb{R}^{C}$ ($C$ variables / channels). The task is to use the past $L$ steps to forecast the next $H$ steps:

$$(x_{t-L+1}, \ldots, x_t) \;\longrightarrow\; (\hat{x}_{t+1}, \ldots, \hat{x}_{t+H}),\qquad x_\bullet \in \mathbb{R}^{C}.$$

The only difference from the univariate case is that each time point goes from a single number to a vector — but it is exactly these "relationships inside the vector" that make the problem both harder and more interesting.

## 15.3 Three modelling strategies

| Strategy | Approach | Pros and cons |
|------|------|--------|
| **Channel-independent** | Forecast each variable separately, sharing one set of model weights | Simple, resists overfitting; but does not use relationships between variables |
| **Channel-mixing** | Feed all variables in together and let the model learn cross-relationships | Captures co-movement; but high-dimensional and prone to overfitting |
| **Graph neural networks (GNN)** | Model the relationships between variables explicitly with a graph | Flexible, interpretable; but the graph structure must be defined or learned |

## 15.4 A counter-intuitive fact: independence is often stronger

You would expect "using the relationships between variables" to be better, yet **PatchTST (lecture 10) set new benchmark records with a channel-independent design**. Why?

- **Relationships may be unstable**: a correlation in the training set may change by the test set, so mixing channels amounts to learning noise as well.
- **Curse of dimensionality**: when $C$ is large, the number of cross-variable parameters to estimate explodes, and without enough data the model overfits.
- **The regularizing effect of shared weights**: all variables using the same weights acts as strong regularization, which generalizes better.

So **channel mixing is not better by default** — it pays off only when there is genuinely stable, strong coupling between variables. Once again this echoes the theme of the whole course: try the simple thing first.

## 15.5 When you really need to model the relationships

- **Clear physical / spatial coupling**: road networks, power grids, meteorological fields — the influence of neighbouring nodes is real and stable, and GNNs / spatio-temporal models come into their own.
- **Known lead-lag relationships**: if one variable reliably leads another by a few steps (which the cross-correlation of lecture 4 can reveal), using it as a feature is very valuable.
- **Few variables with strong relationships**: when $C$ is small and the coupling is obvious, the gains of channel mixing outweigh the risk of overfitting.

## 15.6 Practical tips

- **Run a channel-independent baseline first**: treat it as the "linear baseline" of multivariate tasks; channel mixing must prove that it is better.
- **Beware of data leakage**: in the multivariate setting it is easier to accidentally use "other variables that only become available at the same time" — make sure every feature is truly available at forecast time.
- **The iTransformer perspective**: treating **variables** rather than time steps as tokens was an effective compromise in 2024 — it models the relationships between variables while keeping complexity under control.
