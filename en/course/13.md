## 13.1 There is no "best model"

The previous twelve lectures filled a whole toolbox — linear models, ARIMA, ETS, LSTM, Transformers, KUN. The most common question from newcomers is "so which one should I actually use?" The answer: **it depends on the task and the data, not on how new the model is**. This lecture introduces no new models; instead it teaches you how to **choose the tool for the problem**.

## 13.2 First, be clear about the task

"Time series" actually covers several distinct tasks, and model choice branches from here:

| Task | Goal | Common methods |
|------|---------|---------|
| **Forecasting** | Given the past, infer the next few steps | ARIMA / ETS / deep models / KUN |
| **Anomaly detection** | Find abnormal moments | Thresholds on forecast residuals, isolation forest, reconstruction error |
| **Classification** | Decide which class a whole series belongs to | LSTM / TCN / Transformer, features + GBDT |
| **Imputation** | Fill in missing time steps | Interpolation, state-space models, deep imputation |

The main thread of this course is **forecasting**, but confirm the task type before choosing a model — anomaly detection and classification have different evaluation criteria and different model structures.

## 13.3 Turning forecasting into a table: features + GBDT

Between classical models and deep learning lies a very practical middle road: **use a sliding window to turn the series into a table, then apply gradient-boosted trees**.

```
[x₁ … x₅] → x₆      (use the past 5 steps as features to predict the next one)
[x₂ … x₆] → x₇
```

Besides the raw lagged values, you can build a whole set of useful features:

| Feature type | Examples |
|---------|------|
| Lagged values | $x_{t-1}, x_{t-7}, x_{t-30}$ |
| Rolling statistics | 7-day mean, 30-day standard deviation |
| Calendar features | day of week, month, holiday or not |
| Difference features | $x_t - x_{t-1}$, $x_t - x_{t-7}$ |

**LightGBM / XGBoost** reign supreme on such tables: no normalization needed, nonlinearity captured automatically, fast training, and feature importances to inspect. In settings such as retail or demand forecasting, with "rich calendar / promotion features", they are often the most cost-effective choice.

> Note: once tabularized, it is **still a time series** — cross-validation must use `TimeSeriesSplit` (rolling forward in time), never random K-fold, or you will leak data (lecture 2).

## 13.4 Main lines for choosing a model

Mapping "data characteristics" to "model families":

| Data / constraint | Recommended starting point |
|------------|---------|
| Univariate, short series, interpretability required | ARIMA / ETS (lectures 8 and 12) |
| Rich calendar / promotion features | GBDT (this lecture) |
| Medium length, end-to-end | LSTM / GRU / TCN (lecture 9) |
| Long series, multivariate, lots of data | Transformer / PatchTST (lecture 10) |
| Multi-scale, need both speed and accuracy | KUN (lecture 11) |
| Financial / heavy-tailed / spanning orders of magnitude | Log-transform first, then choose a model (lecture 12) |

## 13.5 A pragmatic workflow

```
1. Clarify the task    → forecasting? detection? classification? how far ahead?
2. Look at the data    → length, number of variables, frequency, heavy tails? (lectures 2, 4)
3. Run baselines       → naive / seasonal naive / linear, to set the floor (lecture 3)
4. Climb the ladder    → ARIMA/ETS → GBDT → deep models, comparing each step to the baseline
5. Evaluate honestly   → time-based backtesting, multiple metrics, check residuals (lecture 4)
6. Stop when it's enough → if the gain is marginal, don't add more complexity
```

## 13.6 The golden rules of choosing

- **Simple before complex**: always start from baselines and linear models; a complex model must prove it is better.
- **Match complexity to data volume**: with little data use classical models; deep models only shine with plenty of data.
- **Interpretability is one of the constraints**: many business settings would rather have "an ARIMA they can explain" than "a black box that is 1% better".
- **Count compute and maintenance costs too**: once deployed, a model must be retrained and monitored for drift; simple models are usually less hassle.

> In one sentence: **model selection is not about picking the strongest model, but the one that best fits "task + data + constraints".**
